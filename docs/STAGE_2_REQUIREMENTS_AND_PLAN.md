# Stage 2 – Project Requirements & Development Plan

## 1. Project Title

Write-Through Caching NVMe Accelerator Simulator using Linux and C++

---

## 2. Project Overview

The project is a Linux-based C++17 simulator designed to study write-through caching and NVMe-style storage I/O.

The system implements a baseline write-through cache and an optimized write-through cache.

The optimized implementation uses concurrent request processing, multiple NVMe-style queues, batching, and write coalescing to investigate their effect on storage performance.

The system uses Linux system-level file I/O to perform storage operations and collects performance metrics for comparison.

---

# 3. Problem Statement

A simple write-through cache may process storage requests sequentially and wait for each operation to complete.

This can limit the utilization of parallel storage queues and increase application latency.

The project aims to develop and evaluate an optimized write-through caching architecture capable of processing multiple storage requests concurrently while maintaining write-through behavior.

---

# 4. Project Objectives

The project objectives are:

1. Develop a baseline write-through cache.
2. Develop an optimized write-through cache.
3. Simulate multiple NVMe submission/completion queues.
4. Support concurrent application requests.
5. Implement write batching.
6. Implement write coalescing.
7. Perform storage writes using Linux system-level I/O.
8. Generate configurable workloads.
9. Collect storage performance metrics.
10. Compare baseline and optimized implementations.
11. Analyze latency, throughput, IOPS, and physical write behavior.
12. Maintain the complete project using Git and GitHub.

---

# 5. Functional Requirements

## FR-01: Workload Generation

The system shall generate configurable write workloads.

The workload generator shall support configurable:

- Number of requests
- Address space
- Request distribution
- Number of application threads
- Random or controlled request patterns

---

## FR-02: Write Request Processing

The system shall accept write requests generated by application threads.

Each write request shall contain information required to identify the target storage location and data.

---

## FR-03: Write-Through Cache

The system shall implement a write-through cache.

A write request shall be forwarded to the simulated storage system rather than being treated as complete only because it exists in the cache.

---

## FR-04: Baseline Implementation

The system shall provide a baseline implementation representing a simple write-through approach.

The baseline shall be used as a reference for performance comparison.

---

## FR-05: Optimized Implementation

The system shall provide an optimized write-through implementation.

The optimized implementation shall support:

- Multiple queues
- Concurrent processing
- Batching
- Write coalescing

---

## FR-06: NVMe Queue Simulation

The system shall simulate multiple NVMe-style queues.

Requests shall be distributed among available queues for concurrent processing.

---

## FR-07: Write Batching

The system shall group pending write operations into batches when configured conditions are satisfied.

---

## FR-08: Write Coalescing

The system shall identify repeated writes targeting the same logical address where applicable and reduce unnecessary physical write operations.

---

## FR-09: Linux Storage I/O

The system shall perform storage operations using Linux system-level file I/O mechanisms.

The implementation shall support direct I/O where configured.

---

## FR-10: Concurrency

The system shall support concurrent request processing using multiple threads.

Thread synchronization shall be used to protect shared data structures.

---

## FR-11: Metrics Collection

The system shall collect performance information including:

- Total requests
- Completed requests
- Latency
- Throughput
- IOPS
- Physical writes
- Coalesced writes
- Queue activity

---

## FR-12: Result Generation

The system shall generate output data suitable for further analysis and visualization.

---

## FR-13: Configuration

The system shall allow important workload and simulator parameters to be configured without modifying the core implementation.

---

# 6. Non-Functional Requirements

## NFR-01: Performance

The system should process workloads efficiently and allow comparison between baseline and optimized implementations.

## NFR-02: Reliability

The system should correctly process valid write requests without data corruption within the simulator's defined scope.

## NFR-03: Thread Safety

Shared data structures shall be protected against race conditions during concurrent execution.

## NFR-04: Maintainability

The implementation shall use modular C++ source and header files.

## NFR-05: Configurability

The simulator shall support different workload sizes, queue counts, thread counts, and timing parameters.

## NFR-06: Reproducibility

Experiments should be repeatable using documented configuration parameters.

## NFR-07: Portability

The project shall target a Linux environment using standard C++17 and available Linux system interfaces.

## NFR-08: Documentation

All major modules, experiments, design decisions, and results shall be documented.

## NFR-09: Version Control

Project development shall be maintained using Git and GitHub with meaningful commits.

---

# 15. Risks and Mitigation

| Risk | Mitigation |
|---|---|
| Incorrect concurrent access | Use proper synchronization |
| Performance measurements vary | Repeat experiments using fixed configurations |
| Direct I/O alignment errors | Use properly aligned buffers |
| Large workloads take too long | Start with smaller workloads and scale gradually |
| Storage permissions/issues | Use a controlled backing file |
| Race conditions | Use mutexes and condition variables where required |
| Difficult debugging | Maintain small incremental commits |
